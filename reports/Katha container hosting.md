# Choose Render for Direct GHCR Deployments

As of 25 October 2026, **Render is the clearest fit for deploying Katha’s two independent Docker images from private GHCR**: it supports private GHCR credentials and lets CI trigger each image-backed service with its own deploy hook. That keeps the release path direct, without inserting a registry relay or requiring Railway Pro just to pull private images. Render’s free service is useful for prototypes, not production: it sleeps and Render explicitly says not to use Free for production. For production, choose paid always-on services and align the web image’s port configuration with Render.

## Render connects private GHCR images to separate services

Render supports prebuilt images in private GHCR when workspace registry credentials include a username and token with `read:packages`; the web and API can therefore remain separate image-backed services ([image deployment](https://docs.render.com/deploying-an-image), [environment variables and registry credentials](https://docs.render.com/configure-environment-variables)). CI can call each service’s deploy hook independently, and the response may include a deploy ID, making this a straightforward image-publish-then-trigger pattern ([deploy hooks](https://docs.render.com/deploy-hooks)). Render also provides free managed TLS for `onrender.com` and custom domains, plus configurable HTTP health checks ([TLS](https://docs.render.com/tls), [health checks](https://docs.render.com/health-checks)).

The trade-off is the free tier: instances spin down after 15 minutes idle, can take about a minute to restart, share 750 hours per workspace monthly, and are limited to 0.1 CPU/512 MB, one instance, and ephemeral storage. Render explicitly states Free is not for production; use paid always-on services for a production deployment ([Free instances](https://docs.render.com/free)). Katha’s web image listens on port **80** in local Compose, while Render’s default web-service port is **10000**; align the image’s listener or service port before deployment ([Render image deployment](https://docs.render.com/deploying-an-image)). If Render is selected, the required CI/provider credentials are the workspace GHCR username and `read:packages` token, plus the separate deploy-hook URL for each service; keep the hook URLs in GitHub Actions secrets.

## Railway makes private-image access a plan constraint

Railway supports public GHCR images, but its documentation limits private GHCR credentials to **Pro**, using a classic GitHub PAT ([services](https://docs.railway.com/services)). Free includes $1/month credit, up to 1 vCPU and 0.5 GB per service, one replica, and no custom domains; Hobby costs $5/month with $5 usage credit; Pro costs $20/month with $20 usage credit. Railway domains include automatic SSL, and current custom-domain allowances are zero on Free, two on Hobby, and 20 on Pro ([pricing](https://railway.com/pricing), [public networking](https://docs.railway.com/networking/public-networking)). Its public API supports CI/CD, but the reviewed documentation does not establish a turnkey GHCR-push workflow or a straightforward way to refresh a service to a newly pushed image digest. Railway health checks gate rollout; they are not continuous monitoring ([API](https://docs.railway.com/integrations/api), [health checks](https://docs.railway.com/deployments/healthchecks)).

## Fly.io requires a registry relay for private GHCR

Fly documents deployment from public external registries; its private-image instructions cover Fly’s own registry, not direct private-GHCR pulls. A conservative CI release therefore pulls from private GHCR, retags and pushes into Fly’s registry, then deploys with `FLY_API_TOKEN` ([`fly deploy`](https://docs.fly.io/flyctl/cmd/fly_deploy.md), [Fly registry](https://docs.fly.io/blueprints/using-the-fly-docker-registry.md), [GitHub Actions deployment](https://docs.fly.io/launch/continuous-deployment-with-github-actions.md)). `fly.dev` domains use HTTPS, and custom domains receive automatic certificates ([custom domains](https://docs.fly.io/networking/custom-domain.md)). Fly has no ongoing free tier; the lowest listed 256 MB shared-CPU VM is $2.19/month in the lowest-cost regions, so two cost **$4.38/month before egress**. Trials are limited. Health checks act as deployment/readiness checks, not automatic restarts ([pricing](https://docs.fly.io/about/pricing.md), [health checks](https://docs.fly.io/reference/health-checks.md)).

## Conclusion

Choose **Render** for the shortest supported private-GHCR-to-deploy-hook path, deploying the web and API independently. Treat Free as a prototype environment; use paid always-on services for production. Railway is a viable alternative if Pro and its classic PAT requirement are acceptable, while Fly adds an image-copy step and a per-VM baseline cost.
